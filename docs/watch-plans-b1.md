# 观看计划 B1：私人数据、排序、轮次联动与备份

## 交付边界

B1 仅交付模型、私有接口、计划规则、观看历程联动和 JSON 备份基础，不新增前端入口。B2 再提供编辑详情、计划队列和只读预览；B3 完成快速筛选、推荐加入入口、批量操作和界面层恢复提示。普通“想看”收藏不会自动创建计划，旧数据不扫描、不回填。

计划表达观看意愿，观看状态表达当前进度，[观看历程](watch-history-a3.md) 表达实际发生的操作。修改优先级、计划日期、备注或顺序不改变作品评分、长评、标签、海报、状态、作品更新时间或观看事件。

## 模型与规则

迁移 **0035_watchplanqueue_watchplanoperation_watchplan** 新增三张表：

- `WatchPlanQueue`：每个账号最多一个队列，独立的递增 `revision`。没有计划的 GET 不创建队列。
- `WatchPlan`：每条私人作品最多一个计划。优先级 `1=优先看 / 2=正常安排 / 3=暂不着急`，默认 2；同档位置、计划时间、最多 500 字备注、目的、阶段、本作品轮次编号、历程清空边界和加入时间。
- `WatchPlanOperation`：账号队列内唯一 UUID、请求摘要与收据时间。不保存备注或完整请求，也不建立第二套实际观看日志。

计划时间 `planned_for` 为 `'' / YYYY / YYYY-MM / YYYY-MM-DD`，复用历程的真实日期校验。保留原始精度，可填写过去的日期；不自动改状态、不补某一天、不生成逾期任务或邮件。

加入时按当前状态推导目的：想看→`first`，在看→`continue`，搁置→`resume`，看过→`rewatch`。在看加入后为 `ongoing`，其余为 `pending`。已存在的活跃计划不能重复加入；已完成或移出的计划可重新安排，推导新的目的并追加到同档末尾。

阶段为 `pending / ongoing / completed / archived`。移出计划仅归档，不删除作品或观看历程；普通读取默认只包含待开始与进行中。删除私人作品会级联删除其计划并使队列版本失效；删除账号级联删除队列及收据。

## 轮次与实际观看

计划创建不物化虚拟观看轮次。非重看计划可先关联虚拟第 1 轮，实际观看时才由既有历程服务创建轮次。准备重看只有意图，目标轮次为空，保存当前轮次作为起点；必须明确 `start-rewatch` 才关联新的实际轮次。普通编辑将看过改为在看不会误判重看已开始。

`start` 要同时核对队列版本和 `watch_version`：首次/恢复观看调用历程 `transition`，重看调用 `start-rewatch`。实际日期仅来自明确的 `occurred_on`，不会从 `planned_for` 复制。开始操作与计划推进、事件和幂等收据同事务提交。

原有编辑保存、快捷进度、收藏导入、历程状态变更、撤销均在 `append_event` 内同步相关计划。轮次想看/搁置对应待开始，在看对应进行中，看过对应已完成；不会把另一轮观看误归属于已经完成的旧计划。撤销开始重看后目标轮次作废，计划恢复待开始；下一次明确重看关联新的编号。撤销完成使计划重新活跃时追加至同档末尾，避免覆盖期间用户已调整的队列顺序。

清空观看历程保留优先级、计划时间与备注，并按新的日期未知基线重新核对关联；不保留已删除轮次引用、不重建旧随记。计划备注与实际观看随记分别管理。移出计划不受普通进度联动影响，但清空时会更新失效的轮次命名空间。

## 私有 API

全部接口仅认证本人可用，响应 `private, no-store`，匿名拒绝、其他账号的作品返回 404。私人计划没有加入公共作品、公开手账、共创宇宙或精选快照序列化。

| 接口 | 契约 |
| --- | --- |
| `GET /api/records/<id>/watch-plan/` | `journal.watch-plan.v1`：当前队列 `version`、作品摘要、`plan`（无计划为 null） |
| `POST /api/records/<id>/watch-plan/` | JSON 命令 `enroll / update / remove / start`；返回当前作品与计划、队列版本及 `replayed` |
| `GET /api/watch-plans/` | `journal.watch-plans.v1`：过滤后的全量数量、分页结果、独立队列版本与全账号阶段计数 |
| `POST /api/watch-plans/reorder/` | `journal.watch-plan-order.v1`：完整同档活跃作品排列；返回当前规范顺序、版本及 `replayed` |

每个写命令必填 `version` 与新生成的 `operation_id` UUID。`enroll/update` 允许 `priority/planned_for/note`，update 至少一项且有真实变化；`remove` 无附加参数；`start` 必填 `watch_version`，可选 `occurred_on`。拒绝混入目的、阶段、用户、队列、轮次等不适用字段。

例如读取当前版本后提交加入计划：

```json
{"action":"enroll","version":0,"operation_id":"d5c8dbf6-09bf-4c36-bd38-9eb16d5dd102","priority":1,"planned_for":"2030-02","note":"等当前作品看完再开始"}
```

队列读取支持 `page`、`page_size=1..100`、`state=active|all|pending|ongoing|completed|archived`、`priority=1..3`、`search`、`sort=manual|planned|added`。筛选在分页前进行，`counts_scope: owner_all_plans` 明确阶段计数不受当前筛选影响。作品摘要读取私人名称和实际海报地址。

手动排序为优先级→同档位置→作品编号，不继承主手账“已评分/看过优先”规则。计划时间排序把未定放末尾，加入时间排序按最近加入；这些查看顺序不写回手动位置。改备注不移动，跨档调整追加至新档末尾；极稀疏的导入位置会在接近整数上限时保持相对顺序归一，避免追加溢出。

排序写入必填 `version/operation_id/priority/record_ids`，列表必须是该档完整活跃队列的唯一排列。拒绝局部列表、跨档、重复、外部账号作品和带筛选参数的请求。上移、下移、拖拽可由 B2 统一生成此排列。

## 并发与失败

统一锁顺序为作品主键顺序→账号队列。单作品命令先锁作品再锁队列，排序和队列读取先锁全部本人作品，后锁队列。原历程接口已锁作品，联动只在其后锁队列。导入沿用用户→作品→配置，再锁队列。规划修改不修改 `watch_revision`，实际开始必须同时校验两类版本。

旧版本返回 409，不自动覆盖。相同 UUID、完全相同的原始请求和目标重试返回最新规范状态，不重复创建计划或实际观看事件；同编号换内容或目标返回 409。排序重试返回当前真实排列，不把旧排列重新应用。客户端结果不明时应保留原请求与 UUID，不自动生成新编号重复开始。

模型观察、计划同步、队列更新、事件及收据任意失败均回滚。队列递增使用数据库原子加法，避免导入级联删除的失效通知使旧内存版本写回倒退。未知字段、日期、范围及矛盾的完整备份在替换前校验。

## JSON 与恢复确认

外层仍为 `anime-journal` v2。每条记录新增可选 `watch_plan`：null 表示无安排；对象内版本 1，保存全部计划元数据、原始日期精度、顺序、阶段、加入时间和本作品轮次关联。没有数据库主键、账号标识或操作收据。完整备份校验非作废目标轮次、历程边界及阶段一致性。

- 字段存在且为 null：清除对应安排。
- 字段存在且为对象：按文件恢复，再与恢复的实际观看事实核对。
- 旧文件省略字段：按完全相同的私人中日文名称与季度匹配，或同一公共作品记录，保留原计划；歧义拒绝，不猜测合并。
- 文件未包含的作品及计划随整体替换移除；无计划的旧记录仍没有计划。
- 历程被换成较旧或已清空的内容时，保留的计划需要解除失效关联，按现有轮次重新核对，不能伪造开始/完成日期。

导入在恢复实际历程之后恢复计划，目标账号重新建立归属，整批失败回滚。完整备份保留手动相对顺序；相同位置以文件内稳定作品顺序兜底。队列版本不从文件倒灌，恢复会使旧队列版本失效，已有操作收据不会把旧请求重新应用到新作品主键。

恢复预览接口增加 `plans_in_file / replaced_plans / preserved_plans / cleared_plans / removed_plans`。确认签名同时绑定当前计划与队列版本，因此只改备注或顺序也会使旧确认失效。现有网页尚未展示这些新增计划计数，界面提示在后续阶段接入。

## 验证与发布

B1 专项 30 项测试，覆盖只读不创建、四种目的、字段归属、稳定排序、全量分页、原 UUID 重试、首次/恢复/重看、完成与撤销、清空、级联删除、隐私、完整/旧格式/null 备份、跨账号恢复归属、恢复失败回滚、稀疏顺序上限和歧义匹配。真实 PostgreSQL 双连接验证初次加入竞争、相同 UUID 开始、计划修改与完成、全队列排序与另一作品开始的锁顺序。

含 B1 在内的 131 项 PostgreSQL 关联回归通过，覆盖既有历程、清空恢复、海报备份和手账/公开接口；前端现有 495 项测试与生产构建保持通过。没有新增界面，不以浏览器截图代替 B1 接口与事务验收。使用隔离配置和本机专用 PostgreSQL，未执行生产迁移或真实账号写入。

发布前备份，先应用 **0035**，再更新后端。无新增依赖、环境变量或邮件/定时任务。B1 可以先上线后端，但用户暂时看不到计划入口；B2 发布界面时使用本契约。启用计划后回退旧导入实现可能丢弃新字段，应保留新版备份并使用支持计划的新后端恢复。
