# N2-2 续：作品审核台账与关闭式全链路

日期：2026-10-21。本轮先完成前置部署版本的两个授权账号只读验收，再按用户确认的边界开发。**审核台账和失效机制已实现，不代表真实成人推荐已接通。**

## 1. 审核语义与不做事项

- 缺少审核记录视为待审核，不因 NSFW 标记自动通过，不在 GET 时自动建档。
- 管理状态：pending / approved / rejected / revoked。内部实时状态还包括 unreviewed、stale、expired、unknown_rating。
- 审核仅为将来成人扩展范围提供人工结论；普通明确安全的 V1 目录不新增“必须先人工审核”的门槛，不因此减少现有安全作品池或改变排序。
- 审核通过不等于成年资格、不等于推荐放行，也不构成系统自动验证合法性的声明。所有现有成人范围请求仍 403，安全范围的成人/未知详情、加入与反馈仍拒绝。
- 不添加前端 NSFW 开关，不改变自动画像、公共展示、用户评分/长评/私人标签，不下载原图、不调用外部 AI 或身份服务。
- 可信成年依据未配置；尚不能开放真实成人推荐。未来开放仍必须另行确认年龄保障、逐作品实际审核与责任、受限媒体交付、前端范围会话及部署门槛；不能把本轮台账当成已完成这些事项。

## 2. 数据模型与增量迁移

`recommendations.0008_content_review` 只建结构及约束，没有数据回填、自动审核或权限分配：

| 模型 | 职责 |
| --- | --- |
| RecommendationContentReview | 每目录作品唯一的一份当前结论；独立 review_version、审核规则、作品资料指纹、内部依据编号、人工排除确认、审核人及截止时间 |
| RecommendationContentReviewEvent | 事务内追加的操作回执/审计；操作 UUID、前后状态/版本、原因、依据编号与当时指纹/规则 |
| RecommendationContentReviewState | 单例全局审核变更版本；仅显式真实变更递增，GET 不创建行 |

审核对象为公共推荐作品及其明确 Bangumi ID，不是私人手账记录 ID。审核记录用 OneToOne 保证作品唯一；操作回执按审核记录 + UUID 唯一；状态、版本范围及单例主键均有数据库约束。审核及回执保护目录物理删除，不能通过默认后台删除来绕过留痕。

审计在应用服务和后台入口内仅追加；不是对数据库管理员的防篡改保证。审核人账号删除时外键置空，保留审核/操作记录，不复制账号私人材料。

## 3. 人工单作品审核服务

- 管理者必须启用、为 staff，并具有独立 `recommendations.manage_content_review` 权限；资格管理权限不等于作品审核权限。写入重新读取权限，不依赖旧对象权限缓存。
- 只提供内部服务和 Django 管理入口，没有公开的用户审核/批准 API，也没有批量批准操作。
- 每次提交绑定 expected_version、expected_catalog_revision、expected_policy_version、operation_id 和审核原因。资料或规则变更后必须重新读取，不能用旧页面确认新资料。
- approve 只接受明确 `nsfw=True` 的作品；必须填内部依据编号，并明确确认已人工排除未成年人或年龄不明人物的性内容等禁止情形。未知分级不可能通过；普通安全 V1 不借该操作重新放行。
- 内部依据只存编号，不上传材料、不接收外链、不发起网络请求。确认框记录人工责任，不是自动内容识别、年龄核验或合法性证明。
- 审核通过默认 30 天，最多 30 天；到期立即内部判无效，读取不写库。重新通过必须以最新版本/资料/规则再次人工确认。
- 指纹绑定现有作品身份、完整名称、季度/类型、分级、题材、简介及封面引用等实际资料；不是通过标题/简介猜题材、身份或系列。资料或规则变化使旧通过结论 stale。
- 内部有效性读取使用当前目录与审核记录的一条联合查询，不能信任调用者持有的旧模型对象；后台显示的资料与签名绑定的指纹来自同一读取。

锁序：作品目录行 → 全局审核状态行 → 作品审核 → 审计回执。同作品并发受目录行锁串行；不同作品争用全局状态行，保证首次建立和递增不丢更新。审核与审计/计数器在同一原子事务，回执失败全部回滚。

相同 UUID/内容重试返回当前最新结论，不重放旧批准。相同编号改内容、旧版本、旧资料/规则为 409。版本到达上限拒绝写入，不归零；重复的同状态待审核不重复增加版本，但保留操作回执。

## 4. 管理后台

入口：`/admin/recommendations/recommendationcontentreview/`。

1. 点击“按 Bangumi ID 读取单部作品”，核对完整名称、季度、类型及分级。GET 不建档。
2. 选择建立待审核/通过/拒绝/撤销，填写原因与通过所需的依据编号、禁止内容排除确认、有效天数。
3. 勾选本次单作品确认，再提交。不能一键批量审核目录。

签名凭据绑定操作者、作品、版本、资料指纹、规则、操作 UUID，15 分钟过期；沿用后台 Session/CSRF。资料变化、旧票据或权限撤销不能覆盖最新结论。失败保留表单，提示重新读取。

审核字段和审计页均只读，无默认新增/修改/删除/批量动作；全局版本单例不注册成可编辑后台。页面不渲染封面，不自动展示/获取媒体，也没有把资料库 NSFW 布尔值当作审核证据。

## 5. 推荐关闭式全链路

放行规则标识升级为 `release-review.ledger.closed.v1`，新增 `content_review_version`：

- 范围解析仍在任何作品/资格查询前拒绝 include_adult，不存在实际放行路径。
- 列表、详情、证据、旧分页 HMAC、固定批次签名、上下文探针与写入前置条件绑定审核版本；审核真实变更使旧上下文返回 409。
- 全局审核版本表示公共目录治理变化，不是某用户偏好；可以使多个用户旧快照失效，但不会更改他们的偏好、反馈、画像或手账。
- scope 读取通过现有本人查询的一个标量子查询取版本，没有按卡片读取审核台账、原因或依据；没有私有共享缓存。普通 V1 排序函数与历史 AST 基线不变。
- 作品审核也会锁目录行，加入/反馈现在在取得目录锁后再次检查范围，防止目录锁等待期间审核上下文已经变更。旧状态不能在等待后直接写入。
- GET 仍在浏览只读事务结束后复查范围，丢弃迟到旧依据；已成功提交的写入不在响应末尾被误报为保存失败。
- 成人目录审核过期/资料变更在内部实时判无效，但当前安全范围本来就不包含这些作品。未来真实开放时还必须逐候选复核并限制快照期限；不能只依赖全局计数器或缓存 TTL。本轮没有声称完成开放后的成人候选计算。

## 6. 部署与回退

1. 必须在新服务承接流量前应用 `python manage.py migrate --noinput`，确认 `recommendations.0008_content_review`。先迁移、后切换新应用；没有迁移时明确 503，不能静默忽略台账依赖。
2. 不为测试账号自动授权，不配置模拟成年依据，不开启 NSFW、不切换 V2；迁移本身不会创建任何审核结论或赋予审核人权限。
3. 完成后按用户授权执行只读脚本；脚本现要求 ledger.closed.v1 及 content_review_version，不能用本轮前置旧版本验收来替代。管理员另做只读页面检查，不为验收提交真实审核。
4. 新旧实例切换期间旧游标/证据可能 409，完成部署后重新加载第一页。公共索引仍只缓存安全公共特征，不存审核原因或用户数据。
5. 回退应用代码至本轮之前的关闭式 N2-2，保留 0008 表、审核与审计，不反向删表。旧应用不使用审核台账且成人仍关闭，不影响原有安全 V1 数据。

## 7. 验证记录

所有写入/并发验证均限定本机独立 PostgreSQL `test_recommendation_isolated_tests`，未使用生产 Neon 或 SQLite。

专项 70 项通过，覆盖新台账、后台、既有资格/范围、上下文探针及只读脚本保护；随后强化“旧模型对象不能代表当前审核资料”的读取后，新台账 18 项再次通过。

完整回归执行 1,056 项（349.384 秒）：1,054 通过、1 项既有真实样本测试跳过；唯一失败为旧隐私断言把新审核表名中的 `review` 子串误认为私人长评列。改为准确匹配 `"review"` 列后，台账、浏览闭环和只读脚本保护 58 项补测全部通过（30.759 秒），包含新加的两项目录锁等待测试。没有通过忽略真实长评查询来放宽隐私要求。

最终新台账测试共 20 项，其中 5 项 PostgreSQL 并发测试：同 UUID 重复审核、通过与撤销同版本竞争、不同作品首次建立全局版本并发、加入等待目录锁期间审核变更、反馈等待目录锁期间审核变更。后两项通过 pg_stat_activity 的 Lock 等待确认真实锁竞争，再验证 409 和零业务写入。

前端现有 250 项全部通过（没有前端代码修改）；Django 检查与迁移漂移检查通过，新增迁移仅 `0008_content_review`。本轮没有在生产签发资格、审核作品或运行迁移，也没有对新管理页做生产浏览器视觉验收。
