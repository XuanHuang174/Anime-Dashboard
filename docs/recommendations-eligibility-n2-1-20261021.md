# N2-1：资格记录、后台安全操作与版本服务

日期：2026-10-21。范围仅资格管理，不是成人推荐上线。N1 封闭合同和 V1 安全过滤均不变。

## 交付

- `RecommendationContentEligibility`：每用户唯一的资格记录、独立 `eligibility_version`、有效期、服务端依据的最小引用。
- `RecommendationEligibilityEvent`：事务内追加的操作审计兼幂等回执，记录操作人、操作、原因、前后状态/版本和期限，不复制手账内容或身份材料。
- 增量迁移 `0007_content_eligibility`：仅建表和约束；没有数据回填、账号授权或管理权限自动分配。
- 单账号后台确认页；本人状态读取/主动停用 API；明确权限、版本及并发保护。
- 没有修改 React 页面、V1/V2 排序、推荐上下文、现有安全目录、公开搜索、封面或资源服务。

## 当前明确关闭的能力

`age_assurance.current_age_assurance()` 是尚未配置的本地权威接口，目前始终返回 `unavailable`。不存在可通过 `.env` 设置的验证器注册或成年人开关，不接收客户端年龄、确认声明或身份材料，也不调用任何外部服务。

因此当前正式代码：

- 可以明确建立待审核记录、撤销或本人停用。
- 签发/续期在没有可信依据时会明确失败，不新增 active 记录、不延长期限；原有签发记录保留管理历史，但实时判定无效。
- 签发分支只在独立 PostgreSQL 中替换权威接口后，以合成依据验证；模拟不等于真实年龄验证。
- `adult_access_allowed=false`、`serving_integration=false`、`effective_scope=safe` 始终固定。即使隔离测试中的资格有效，现有推荐路由仍拒绝成人与未知分级。
- 下一阶段必须单独确认并实现权威依据来源、作品放行审核及全链路上下文校验；本阶段不能通过设置一个变量直接开放。

## 状态与期限

| 记录/事件 | 规则 |
| --- | --- |
| 未建立记录 | GET 返回 `not_requested` / 版本 0，不写数据库 |
| 建立待审核 | 显式操作，生成 pending 记录与审计，不构成签发 |
| 签发 | 专门管理权限、目标非本人且账号启用；服务端依据已核验、未过期、与目标账号一致 |
| 续期 | 已有 active 记录才可重新核验；已撤销必须走重新签发，不能复活旧续期请求 |
| 撤销/本人停用 | 写入 revoked，保留独立版本和操作回执，不删除手账或资格历史 |
| 到期 | 读取时比较当前时间，截止时刻即无效，不等待 cron、不做 GET 写入 |
| 依据撤销/故障/版本改变 | 当前资格判定立即不再有效，不能继续相信已存的旧证明 |

首轮用途固定 `internal_test`，签发/续期默认 30 天、最多 30 天；实际截止不得超过服务端依据截止时间。续期是新的人工确认操作，不会自动续期。

续期不得反向缩短已有期限；如需缩短/终止，应明确撤销，而不是借续期操作静默改变语义。

真实状态变更递增版本；同状态的重复操作不重复递增，但保留幂等回执。版本达到上限时明确拒绝新变更，不循环归零。

## 权限、事务与幂等

- 管理者必须是启用的 staff，并具有 `recommendations.manage_content_eligibility` 专门权限；仅 staff 不足以操作。
- 服务重新读取操作人的权限，不能用请求对象上缓存的旧权限绕过已撤销的管理权。
- 管理员/超级用户身份不等于浏览资格。不能为自己签发或续期。
- 所有写入锁顺序：目标用户行 → 资格行 → 操作回执。与已有加入想看/反馈的用户行锁顺序兼容。
- 所有写入使用同一原子事务；审计写入失败则资格变更一并回滚。
- `expected_version` 和 UUID `operation_id` 必填。相同编号/内容重试仅返回回执与**当前**资格状态，不重放历史签发或撤销。
- 同一编号改内容、陈旧版本、错误状态转换返回 409，不静默覆盖。续期与撤销竞争时只能一个提交，另一方需重新读取并确认。
- 资格版本不同于偏好/反馈版本，本轮不更改这两者，也不触发普通 V1 推荐列表刷新。
- 回执在应用服务与后台入口内仅追加，不提供修改/删除或批量操作；这不是对数据库管理员的防篡改保证。账号物理删除遵循外键清理，不改变既有账号删除语义。

## 用户 API（暂无前端面板）

`GET /api/recommendations/eligibility/`

- 登录后仅读取 `request.user`；不接受其他用户 ID 或任何查询条件。
- 返回管理状态、实时有效状态、独立版本、有效期、依据状态和上下文指纹；不返回管理原因、操作人、依据引用或其他账号信息。
- 响应 `private, no-store`，并按 Authorization/Cookie 区分。
- 上下文指纹不是授权令牌；N2-2 不能据其自行认定权限。

`POST /api/recommendations/eligibility/revoke/`

```json
{"expected_version": 0, "operation_id": "由客户端生成并在重试时复用的UUID", "confirmed": true}
```

- 只能停用本人资格，不能携带目标用户、状态或依据字段。
- 无记录时也会留下显式停用的版本 1 记录，避免先前版本 0 的审核请求随后意外覆盖。
- 不提供公开的签发、续期、重新激活或自助修改资格字段接口。
- 缺少迁移/数据库故障时新资格 API 返回 503，不将异常解释为有效资格；现有推荐接口不依赖新表。

## Django 后台操作

入口：`/admin/recommendations/recommendationcontenteligibility/`。

1. 有管理权限的人员点击“选择账号并核对资格”，输入目标账号 ID。
2. 读取账号名称、ID、当前状态、版本和期限；GET 不建立记录。
3. 选择单项操作，填写原因/期限，明确勾选确认，再提交。
4. 服务执行；失败保留表单并提示。409 需点击重新读取，不能绕过旧版本。

操作凭据签名绑定操作者、目标账号、预期版本及操作 UUID，15 分钟过期；同时保留 Django 后台正常登录与 CSRF 保护。不得将该后台签名当作用户浏览权限令牌。

资格字段和审计记录均只读，禁止默认 add/change/delete 与批量操作。签发/续期选项当前会因可信依据未配置而明确拒绝，这是预期行为，不是部署遗漏。原因不得填写身份证、出生日期、私人评分或长评。

## 测试与验收边界

隔离配置：`config.recommendation_pg_test_settings`，数据库必须是本机 `test_recommendation_isolated_tests`；禁止 SQLite/生产 Neon。

覆盖：未授权/旧权限/自签、无来源及错账号依据、期限与到期、来源故障/变更、幂等重放不复活、版本冲突/上限、事务审计回滚、唯一/状态约束、本人隔离、后台签名/确认/CSRF、原记录逐字段不变，以及有效合成资格也不能开放旧路由。

四项真实 PostgreSQL 竞争：同 UUID 重复签发、不同 UUID 同版本竞争、续期与撤销竞争、撤销与加入已有作品竞争。没有在真实账号上制造资格或修改手账数据。

执行结果：完整后端回归 1,013 项，1,012 通过、1 项既有真实样本跳过（322.008 秒）；最终专项 32 项全通过，包含本阶段新增 24 项和 N1 合同 8 项。前端既有 250 项回归全通过；Django 检查和迁移漂移检查通过。本轮没有部署后的浏览器视觉验收。

## 部署与回退

1. 发布本轮代码后，在部署环境运行 `python manage.py migrate --noinput`，确认 `recommendations.0007_content_eligibility` 已应用；按项目部署方式安排迁移与应用更新顺序。
2. 不开启 NSFW，不配置“模拟验证器”，不自动为测试账号授权；当前仍是关闭阶段。
3. 只读验收应检查：本人状态接口、后台只读页面、无资格默认拒绝、已有普通推荐可用。正式签发/撤销写入需另行明确授权，不能在只读验收时执行。
4. 回退应用代码即可恢复前置行为，保留新增表/审计/版本，不运行回退删表迁移、不清除手账、偏好或反馈。
5. 后续需要人工明确的事项：可信年龄依据的实际来源及撤销机制、作品放行规则、N2-2/N2-3 全链路接入。尚不具备公开成人内容的上线条件。
