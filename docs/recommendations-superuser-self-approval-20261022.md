# 超级管理员本人授权：明确确认、审计与兼容修正

日期：2026-10-22（UTC+8）。用户已明确同意调整“禁止管理员审批本人申请”的原规则。

## 问题与新边界

旧后端在审批人与申请人相同时直接拒绝，而模块 3 前端又把具体原因显示为笼统错误。截图未勾选确认框也会使按钮禁用，但即使勾选，旧后端的自审禁令仍会阻止批准。

现在允许**当前有效、活跃且有 staff 身份的超级管理员**审批本人待审批申请；不按 `XHcode` 用户名硬编码，不给管理员自动授权，不给普通用户／普通 staff 开放自审。

同时必须满足：

- 已有本人主动提交的有效待审批申请；不能无申请直接签发。
- 明确审批原因，1–30 天有效期，不自动续期。
- 原审批确认与新增“本人授权／自审”确认均为明确布尔 true；字符串或数字不能代替。
- 模块 3 原签名票据仍绑定操作者、目标、版本及操作 UUID，15 分钟有效；版本冲突不能覆盖。
- 数据库用户行锁后重新读取实际权限；排队期间失去超级管理员权限时仍拒绝。

人工授权仍不是年龄核验，不修改作品审核规则，不开启总开关，不改变默认安全范围、V1 排序或用户手账。

## 实现

### 服务和审计

`recommendations.eligibility.mutate_eligibility` 复用原事务、用户锁、版本、幂等回执与期限逻辑。自审批准额外要求 `confirmed=True`、`self_approval_confirmed=True`，缺失时返回明确的 `self_approval_confirmation_required` 校验错误。

新增审计字段 `RecommendationEligibilityEvent.is_self_approval`。该值由服务根据操作者／目标及操作推导，不能由客户端直接指定。原申请、拒绝、撤销和其他账号的审批均不标记自审。数据库约束禁止将非 `approve` 事件标为自审。

自审事件保留操作者、目标、原因、期限、前后版本、操作 UUID、指纹和时间；审计失败则整个授权事务回滚。重放旧批准请求只返回当前状态，不能在撤销之后重新授予权限。

### 模块 3 与 Django 管理后台

- 模块 3 申请详情增加服务端 `is_self` 与本人授权能力标识，不从用户名推断权限。
- 本人批准显示额外确认框，默认不勾选；选择账号、切换操作、取消或重读后重置。缺少普通确认／本人确认或原因时不提交。
- Django 原有“核对与管理”页面同样要求独立本人确认，不保留第二条绕过服务的授权路径。
- 审计列表可显示／筛选“超级管理员本人授权”。
- 模块 3 区分本人确认不足、版本冲突、权限丢失、旧后端自审禁令与输入错误；不把服务器堆栈或任意 HTML 响应直接显示出来。
- 正常审批其他用户的流程不增加本人确认项，不改变已有回执指纹。网络提交结果不确定时仍重试原操作，不创建新的授权决定。

## 迁移与部署

新增迁移 `0011_eligibility_self_approval_audit`，只为审计表增加字段和约束，不修改任何申请、授权、作品或手账记录。

字段同时使用 Python `default=False` 与 PostgreSQL 持久 `db_default=False`：历史事件默认不是自审；滚动部署中旧实例省略新字段写入时也能成功，不会因为新 NOT NULL 字段导致旧实例审计写入失败。

发布时按现有部署流程执行：

```text
python manage.py migrate --noinput
```

确认 `0011_eligibility_self_approval_audit` 应用后再让新代码接受授权写入，并发布匹配前端。无需清空用户缓存、重新申请、删除旧申请或恢复评分；XHcode 当前待审批申请可以重新读取后继续处理。

后端先升级时旧前端不会提交本人额外确认，因此本人批准仍被拒绝，不会被默许。新前端遇到旧后端的明确自审拒绝会提示确认后端版本。

回退代码时保留新增字段／约束及审计记录，不反向执行迁移抹去自审标识。旧后端仍会拒绝新自审；已经批准的授权不会因代码回退自动撤销，如需撤销应走原审计服务。异常时可先持久关闭模块 3 服务，不重置版本、不删业务数据。

## 部署后的操作

1. XHcode 登录模块 3，重新读取本人当前待审批申请。
2. 点击“批准申请”，填写原因和期限，分别勾选审批确认、本人授权确认，再提交。
3. 在“推荐资格操作审计”检查该笔批准的“超级管理员本人授权”为真、操作者和申请人为本人。
4. 已审批的两个测试账号无需重新申请。未知分级、安全过滤、作品审核和开闸流程仍照常生效。
