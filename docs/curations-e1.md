# E1：主题片单数据、私人接口与备份基础

E1 完成手动主题片单的服务端基础，以及现有 JSON 恢复面板的片单影响提示。片单首页、选片和编排界面由 E2 接入；手账／推荐／回顾入口、图片导出及完整页面验收留在 E3。片单主功能暂不标为全部交付。

## 数据与边界

迁移 **0037_curationlibrary_curationlist_curationentry_and_more** 新增四张表：本人片单库及单调版本、片单、成员条目、操作回执。私人片单与条目分别使用所属账号／片单内唯一的 UUID，数据库行号仅在当前账号的私人作品操作中使用。标题允许重名，以 UUID 区分。

片单包含名称、简介、置顶、归档、创建顺序和可选封面条目。条目包含明确选择的私人作品、独立入选理由、手动顺序和最小名称快照。成员在同一片单内唯一，同一作品可进入多张片单。排序以位置及数据库主键稳定确定；首页先置顶、再按创建顺序。封面默认取首个可用成员，也可选择本片单内可用成员；所选成员失效时回退，移出该成员时清除封面选择。

操作不改作品评分、长评、标签、观看状态、历程或计划，不自动加入推荐候选、不创建观看事件。读取时显示当前私人作品资料、评分及进度；排序和入选理由独立保存，作品资料变化不自动改变成员。每账号最多 100 张片单，每张 500 项，合计 5000 项；单次添加最多 100 部，整批验证后写入，超限或混入不可访问作品整批失败。

## 私人 API

接口仅认证本人可用，不提供公开片单接口。成功及错误响应均为 `private, no-store`，并区分 Authorization／Cookie。公开手账和现有作品序列化不增加片单标题或入选理由。

| 接口 | 行为 |
| --- | --- |
| `GET /api/curations/` | 本人片单分页；支持 `search`、`state=active/archived/all`、`pinned=any/true/false` |
| `GET /api/curations/<UUID>/` | 本人片单信息和有序成员分页 |
| `POST /api/curations/` | 明确的片单或成员操作 |
| `GET /api/records/<ID>/curation-impact/` | 删除作品涉及的片单及保留规则，供 E2 提示使用 |

响应契约为 `journal.curations.v1`，包含账号片单库 `version`。分页默认 20、最多 100，返回完整匹配数量及下一页；第二页起必须携带原版本，版本变化返回 409。未建立片单的 GET 返回版本 0 和空结果，不创建数据库状态。首页成员预加载，不逐条读取海报作品资料。

所有 POST 须包含 `action / version / operation_id`。支持：

| action | 主要字段 |
| --- | --- |
| `create` | `title`，可选 `description / pinned / archived` |
| `update` | `list_id` 和至少一项 `title / description / pinned / archived / cover_entry_id` |
| `delete` | `list_id`，仅删除片单及其编排 |
| `add` | `list_id / record_ids`，按请求顺序追加，已收录作品保留原条目 |
| `update-entry` | `list_id / entry_id / reason` |
| `remove-entry` | `list_id / entry_id`，保留私人作品 |
| `relink` | `list_id / entry_id / record_id`，仅对失效条目明确重新关联 |
| `reorder` | `list_id / entry_ids`，须为含失效条目的完整、不重复成员集合 |

名称最长 80，简介和入选理由各 2000 字符。拒绝未知、不适用字段、伪造账号、错误类型及跨片单成员／封面。写入事务首先锁账号，再按主键锁相关作品、锁片单库；与导入恢复及作品删除保持共同账号锁。版本过期返回 409；同一操作 UUID、相同请求可重试，返回当前规范状态，不重复添加／创建。换请求复用 UUID 被拒绝，已删除片单的旧回执不会使片单复活。

## 删除作品

通过 API、ORM 或后台删除作品时，删除前更新成员的最小名称快照，随后将作品引用置空，保留条目 UUID、位置和入选理由，并提升片单库版本。读取返回 `unavailable=true / record=null`。同名作品重新加入手账不会自动接回旧条目；须显式 `relink`，且不能与片单已有成员重复。删除账号则完整级联移除其片单库、条目和回执，不重建状态。

## JSON 备份与恢复

沿用 `anime-journal` v2 的顶层格式及现有 5MB 导入文件上限，增加可选 `curations: {version: 1, lists: [...]}`；每部导出作品新增文件内 `record_ref`（如 `r0`）。片单及成员 UUID、简介、理由、封面选择和数组顺序一并导出；成员通过 `record_ref` 引用本文件中的作品，失效成员引用为 null。备份不存片单数据库行号，不抓取图片或创建公开报告。

恢复严格校验片单格式／版本、数量、UUID 唯一性、成员唯一性、文件内作品引用及封面归属，然后在同一事务中将引用映射为新建私人作品。恢复到其他账号仍指向目标账号的作品，片单 UUID 的账号作用域互不冲突。任一步失败，原作品、片单、理由、版本及回执整体保留。

- 文件包含 `curations`：以文件完整替换本人片单，明确空 `lists` 表示清除本人片单。
- 旧文件未包含该字段：保留现有片单、UUID、顺序和理由，仅在中文名、原名、季度准确且唯一匹配时重接现有可用成员；文件未包含或身份不明确的作品保留为失效条目。原已失效成员不按名称自动重新关联。
- 恢复预览展示新增、替换、移除、保留片单数，以及恢复后关联／待重新关联条目数；预览不写入。
- 确认凭据同时绑定文件片单内容和当前片单库、成员及版本。预览后编辑理由、成员或片单，原确认立即失效；不会覆盖预览后发生的修改。

旧版服务端不了解片单扩展；含片单的备份应使用支持 E1 的导入端，避免回退版本丢失编排。

## 验证与部署

本机隔离 PostgreSQL 141 项关联回归通过，涵盖 E1 专项 24 项以及原计划、历程、恢复、海报备份、月度和年度回顾。并发验证首次创建竞争、相同 UUID 只写一次、理由编辑与已确认恢复竞争，以及作品删除与理由编辑的锁顺序。SQLite 专项通过，4 项仅 PostgreSQL 并发测试明确跳过。

533 项前端测试及生产构建通过，保留已有大分包提示。真实本地浏览器验证恢复新增／替换／移除和失效条目说明、预览只读、320／390／1440px 布局、修改理由后拒绝原恢复，以及公开页无片单读取和私人理由泄漏。

复跑：后端使用 `config.recommendation_test_settings`；并发使用受限本机 `config.recommendation_pg_test_settings`。关联功能测试可在进程内提高 account 读写节流预算，防止测试复用用户编号累计限流，不修改生产配置。浏览器仅使用 `config.journal_polish_e2e_settings` 和 `.tools/watch-history-a3.sqlite3`，先迁移，再执行 `scripts/seed-curations-e1-e2e.py`；启动 8000 后端、5191 前端，在 frontend 执行 `node scripts/test-curations-e1.mjs` 并设置本机 `PLAYWRIGHT_MODULE`。凭据、数据库、截图和日志仅在忽略的 `.tools`，没有访问生产数据库。

发布顺序：**备份 → 应用迁移 0037 → 更新后端 → 发布前端**。无新增依赖或环境变量。E1 部署后可在恢复预览看到片单影响，新增“片单”工作区入口将在 E2 交付。
