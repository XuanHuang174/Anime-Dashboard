# 手账海报备份、公开来源与精选后台修复

## 海报往返契约

私人页面按 `poster_image || poster_url` 显示海报，JSON 备份也采用相同顺序，将实际使用的地址写入 `records[].anime.poster_url`。备份格式继续为 `anime-journal` v2，不增加依赖；评分配置等原有内容不变。

- 图片字段存在时优先使用其存储 URL；原 `poster_url` 仅为备用地址，可能仍指向早期图片代理。
- 恢复只保存指定 URL，不重新下载图片、不进行智能录入、不替换域名，不把远程 URL 当作 ImageField 的存储键。
- 兼容已有 API 形状的 JSON：非空 `anime.poster_image` 优先于 `anime.poster_url`；两者均未提供可用值时兼容 `anime.cover`。空图片字段不遮盖已有 URL。
- 非空字段必须是有效 HTTP/HTTPS URL；临时 blob、本地文件、相对路径、非字符串及携带用户名密码的地址返回记录级字段错误，在整体替换前终止。完全未填写海报时仍允许空值。
- URL 中路径、查询串和域名不被改写；既有智能录入的海报持久化流程保持原样。
- 备份保存地址，不打包图片二进制。已经只剩代理地址的旧备份不会猜测其对应的媒体对象路径；可从保留原 media 地址的备份恢复。

## 公开资料链接

公开手账、公开首页、后台公开手账审核列表预加载记录的标准作品关联。来源解析先使用已核验来源或公共权威 ID，再检查已加载的私人关联是否有效、记录和目录指纹是否仍匹配。公开读取不对每部作品单独查询关联，不向客户端返回关联凭据。

手动保存的 Bangumi 条目链接继续展示；有效关联可生成标准 `https://bgm.tv/subject/<ID>`。失效或过期指纹的关联不生成链接，也不按片名猜测。前端继续统一验证目标网址，缺失时显示“未设置”。

## 投稿快照

`FeaturedSubmission.bangumi_url` 是投稿时保存的只读链接快照，新投稿从当时的有效资料复制链接。用户端、审核接口和公共精选接口均返回该快照，前端映射到 `bangumiUrl`。已有投稿由迁移填空，不自动回填，不随作者之后的私人修改改变。

## Django 后台

生产日志确认超时发生在投稿详情的普通关联下拉框渲染中：表单遍历私人记录，通过 `UserAnimeRecord.__str__` 逐条查询用户，最终触发 Gunicorn `WORKER TIMEOUT`。日志中的关联缓存 `KeyError: user` 是触发数据库读取的过程，不代表用户丢失。

- 已有投稿的用户、来源作品、来源私人记录改为只读，避免全量选择和误改归属；新增表单使用搜索选择。
- 预加载用户、来源作品及被引用记录所需的关联；列表每页 30 条，关闭额外全表总数统计。
- 详情按来源与审核、作品快照、观看与评价、标签与简介、评分与系统信息分组；较长内容默认折叠。
- 列表用简短“打开海报”链接代替长 URL，不在服务端检查外部图片是否存在，不以延长 worker 超时掩盖查询问题。

## 发布与验证

先在后端执行 `python manage.py migrate --noinput`，应用 **0032_featuredsubmission_bangumi_url**，再启动新版后端、发布前端。无需新增环境变量；未执行线上数据修复或旧快照回填。

- 隔离 PostgreSQL 关联回归 148 项通过，覆盖新海报往返、旧字段兼容、非法地址无写入、公开来源一致、失效关联、投稿冻结及既有导入/智能录入。
- 后台真实 GET 渲染验证：新增 150 条无关私人记录后，投稿详情查询数保持有界，表单不出现来源记录全量下拉；仍可修改审核状态。
- 前端 483 项测试及生产构建通过。`test-journal-public-sources.mjs` 用真实详情组件和映射器检查共享手账、新旧精选快照在桌面和 320px 手机下的链接状态、可点击性、布局与页面异常；截图位于忽略目录 `.tools/journal-public-sources-qa/`。
- 原有 `test-journal-filters-b.mjs` 保留详情、筛选和移动端布局回归。本轮所有业务验证使用本地隔离数据库和合成数据。
