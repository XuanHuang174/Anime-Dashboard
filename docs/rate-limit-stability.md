# 限流稳定性修复与部署验收

本次处理匿名浏览、登录/注册/刷新共同被限流的问题。历史事件最可信的解释是 `NUM_PROXIES=0` 与 Render 代理地址共用匿名 `1000/day` 额度；现有截图不能确认当时是否存在攻击。修复验证使用合成请求和隔离数据库，未对生产压测或清理计数。

## 客户端身份

- 本机/普通部署默认 `CLIENT_IP_MODE=direct`：忽略所有转发头。
- Render 自动提供的 `RENDER=true` 会选择 `trusted_proxy`。内置可信列表包括 Render 内网/回环与 Cloudflare 官方代理网段；从 X-Forwarded-For 右侧逐级跳过可信代理，取第一个非可信地址，不依赖固定代理层数。
- 未经信任的直连来源不能用请求头改变身份。客户端伪造的左侧前缀不会参与身份判断。IPv6、IPv4-mapped IPv6 都会规范化。
- 可信代理缺少有效链、链过长或没有找到客户端时返回明确 503，禁止回退为全站共用回环 IP。健康检查 `/` 继续可用。
- 其他部署须按真实网络配置 `CLIENT_IP_TRUSTED_PROXY_CIDRS`（逗号分隔）；不允许 `0.0.0.0/0` 或 `::/0`。不要在普通直连服务上启用 Render 的信任范围。

Cloudflare 网段已于 2026-11-20 对照官方 [IPv4](https://www.cloudflare.com/ips-v4) / [IPv6](https://www.cloudflare.com/ips-v6) 列表核对。平台代理拓扑仍需通过下面的真实请求验收，不能仅靠本地模拟认定线上身份准确。

## 独立额度

| 类别 | 短窗口 | 持续窗口 | 标识 |
|---|---|---|---|
| 公共读取 | 120/分钟 | 2400/小时 | 客户端 IP |
| 普通匿名写入 | 20/分钟 | 100/小时 | 客户端 IP |
| 私人读取 | 240/分钟 | 6000/小时 | 账号 |
| 私人写入 | 120/分钟 | 3000/小时 | 账号 |
| 登录 | 20/分钟 | 100/小时 | 客户端 IP |
| 同账号登录 | 3/分钟 | 上述登录总额度 | IP + 规范化账号 |
| 注册 | 3/分钟 | 20/小时 | 客户端 IP |
| 找回密码邮件 | 3/分钟 | 20/小时 | 客户端 IP |
| 邮箱激活/密码重置确认 | 10/分钟 | 60/小时 | 客户端 IP |
| 刷新令牌 | 60/分钟 | 1000/小时 | 客户端 IP |

推荐保留既有 read/identity/write 的 60/30/30 每分钟专用额度，账号总量从每日改为 6000/小时。外部搜索、导入、海报等原有专项保护继续生效。阈值是本次初始策略，不代表服务器承载能力测试结果。

每一项可用 `RATE_LIMIT_<预算名大写>` 调整，如 `RATE_LIMIT_PUBLIC_READ=120/minute`、`RATE_LIMIT_PUBLIC_READ_HOUR=2400/hour`。只接受正整数与 minute/hour，不接受关闭保护的空值。

限流使用独立 `throttle` 缓存，避免公共推荐缓存淘汰计数。当前依然是每 worker 的 LocMemCache（最多 5000 键），适用于当前轻量部署：它不是跨实例精确额度，重启/淘汰会重建计数，DRF 内置判断也不是原子操作。多 worker/多实例以及强防攻击需求，应另行采用共享原子计数与边缘防护；不要把这次修复描述成 DDoS 防护或负载测试。单个共享公网出口的访客仍会共享按 IP 的认证额度。

## 前端行为

- 刷新遇到 429、网络故障、5xx、异常响应，保留凭据；只在确认刷新令牌 401 或本机确实缺失刷新凭据时退出。
- 429 遵守 Retry-After；其他临时刷新错误等待 10 秒后才允许再次刷新。不会后台自动重放写入。
- 同一页面的并发 401 共用一次刷新；成功后各自重放一次。旧账号的迟到响应不能覆盖/退出新账号。
- 通知仅在页面可见时读取；focus/visibility 合并、错误指数退避，429 遵守服务端等待；同一连续故障只提示一次。
- 首页统计、快捷筛选、筛选选项进入时读取一次，翻页只读取作品列表；管理员权限检查临时失败保留凭据并允许重新验证。
- 等待使用单调时钟；Retry-After 日期优先相对服务端 Date，避免电脑时钟偏差。

## 日志与故障定位

DRF 限流响应含 `code=rate_limited`、`retry_after`、`request_id`、Retry-After 与 X-Request-ID，且 private/no-store。跨域允许前端读取这些响应头。

应用日志输出 JSON，事件包括 `rate_limited`、`client_identity_unavailable`、`rate_limit_store_unavailable`，包含预算名/速率、等待秒数、视图、脱敏客户端与账号标识、可信代理跳数、请求关联 ID。不含原始 IP、用户名、密码、Cookie、令牌或 URL 查询参数。Render 免费计划可在现有应用 Logs 中搜索这些事件，不要求付费 Shell。

根地址返回 `rate_limit_policy=rate-limits.v2` 只证明新版健康接口已部署，不证明登录/业务接口可用。

## 部署与线上验收

1. 正常部署本次前后端，无新增数据库迁移或第三方依赖。Render 的 `RENDER=true` 自动选择代理模式；若此前手动设置了 `CLIENT_IP_MODE=direct`，应改为 `trusted_proxy`。其余现有推荐/系列/Credits 开关不变。
2. 先运行公开检查：

   ```powershell
   .\.venv\Scripts\python.exe scripts/verify_rate_limit_deployment.py --public-only
   ```

3. 然后运行管理员只读检查（密码隐藏输入，不写文件/不输出凭据）：

   ```powershell
   .\.venv\Scripts\python.exe scripts/verify_rate_limit_deployment.py --account XHcode
   ```

   一次正常登录、三次管理员 GET、一次健康 GET，共 5 个请求；不会刷满额度、导入记录或调用邮件接口。`passed_staff_readonly` 表示代理身份来自真实转发链，且两个伪造转发前缀没有改变标识。`failed_or_blocked` 时看 checks 中首个 false 和同时间应用日志；不要无限复跑登录。

4. 换另一网络再运行一次：不同公网 IP 的 `client_fingerprint` 应不同。同一 NAT/VPN 出口可能相同，属于预期。诊断接口 `/api/admin/rate-limit-status/` 仅 staff 可读，普通账号无权查看。
5. 浏览器检查：正常账号登录/读取手账、翻页；后台页面不继续通知轮询；本机模拟刷新 429 时保持登录，等待后能恢复。不要为了验收在生产重复提交写入或制造大量错误登录。

脚本不校验部署前端 bundle、不完成两网络对比或负载验证；这些边界会写入结果。线上验收完成前，不应报告已确认生产代理拓扑或故障彻底消失。

## 应急处理

出现 429 时先保存请求 ID、预算名、等待时间及相邻应用日志。出现身份 503 时核对真实代理链/模式；不要盲目信任最左 IP 或直接放开所有转发头。重部署可以重建进程内计数，但属于临时恢复，不能替代身份与预算诊断。不要清空数据库、全站缓存、账号或令牌。
